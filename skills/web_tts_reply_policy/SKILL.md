# Web TTS 回复规则

当用户消息中包含 `[TTS:auto]` 时，表示本次回复启用了网页端自动语音回复规则。

请按以下规则处理：

1. 如果本次回复适合语音播放，请将适合朗读的自然语言内容放在一个或多个 `<tts>` 和 `</tts>` 之间。
2. 如果本次回复较长，请优先在开头输出一个简短的 `<tts>` 段，用来快速说明结论或回应用户。正文可以继续正常输出。
3. 可以使用多个 `<tts>` 段，分别标记开头说明、过程说明和结尾总结。
4. `<tts>` 内可以使用 Mimo 官方支持的标签控制。
5. 整体风格标签应放在目标文本开头，括号可用半角 `()`、全角 `（）` 或 `[]`，例如：`（温柔）`、`(开心)`、`[粤语]`。
6. 音频标签可插入文本任意位置，例如：`[叹气]`、`[轻笑]`、`[深呼吸]`。
7. 当语音内容适合表达确认、提醒、安抚、总结、轻松互动或情绪变化时，可以主动选择合适的风格标签，例如：`（温柔）`、`（开心）`、`（认真）`、`（轻松）`、`（惊讶）`。
8. 必要时可以少量加入 `[轻笑]`、`[叹气]`、`[深呼吸]` 等音频标签。
9. 保持克制，不要每句话都加标签。
10. 代码、日志、表格、长列表、diff、工具结果不要放入 `<tts>` 标记。
11. `<tts>` 内应写成适合直接口播的自然语言，不要使用 Markdown 列表、横杠项目符号、表格分隔符、引用块、代码式缩进或类似排版符号。例如不要在 `<tts>` 内写 `- 第一项`、`---` 这类格式。正常口播中的“第一、第二、第三”“第一点、第二点”可以使用。
12. 如果正文涉及公式、路径、参数、文件名、命令、diff 或复杂符号，请不要把这些内容放入 `<tts>`；可以在 `<tts>` 内改写成简短自然语言说明，例如“我会先修改配置文件，然后检查构建结果”。
13. 不要依赖前端过滤符号来修正口播文本。应在生成 `<tts>` 内容时主动避免会被语音引擎读错的排版符号。
14. 不要主动使用 `（唱歌）`、`(唱歌)`、`[唱歌]`、`sing` 或 `singing` 标签。只有用户明确要求唱歌、歌词或唱歌模式测试时，才使用唱歌标签。
15. 普通正文仍然正常输出。`<tts>` 段只用于指出适合朗读的部分，不替代完整回答。
