# ASMR 制作流水线设计（草案）

> ⚠️ **本项目是独立工程，不属于 Clonoth/Bot。**
> 本文档只是设计参考，实现代码放在独立仓库/目录中。

> 状态：草案 v0.1
> 日期：2026-10-06

---

## 这个文档在讲什么（人话版）

做一期 ASMR，从头到尾是这么几步：

```
1. 写台本（词 + 音效标注）
2. 把每句话变成语音
3. 找出台本点名的音效文件
4. 混成一条音轨
5. 导出成品
```

这份文档管的是**中间怎么衔接**，就三件事：

- **文件放哪** —— 源文件、临时文件、成品分开摆，别混一起
- **跑到一半崩了怎么办** —— 已经做好的段落存下来，重跑时跳过，不白干
- **混音按什么顺序做** —— 先铺环境音，再叠人声和音效，最后统一调音量

下面开始是具体设计。

本设计借鉴了两个开源有声书管线的成熟做法（**借鉴思路，不照搬代码**）：

| 项目 | 可借鉴之处 |

```
│   └── rainy_library.asmr
├── materials/                # 素材库（人工维护）
│   ├── sfx/                  # 触发音
│   │   ├── page_turn_01.wav
│   │   └── ...
│   ├── bed/                  # 环境音底
│   └── index.yaml            # 素材清单
├── presets/
│   └── beds.yaml             # 环境音预设定义
├── build/                    # 工作目录（可整目录删除后重建）
│   ├── timeline.json         # 冻结的时间轴
│   ├── events.json           # 素材匹配结果
│   ├── resume.json           # 续跑清单
│   └── logs/
├── cache/                    # 内容寻址缓存（可清，后果只是重算）
│   ├── tts/                  # 分段 TTS 产物
│   └── mix/                  # 混音中间产物
└── output/
    └── rainy_library.wav
```

**四层职责切分**：

| 目录 | 能否删 | 说明 |
|---|---|---|
| `scripts/` `materials/` `presets/` | ❌ 源数据 | 人工维护，是项目的真正资产 |
| `build/` | ✅ 可删 | 删了会重算，但结果一致 |
| `cache/` | ✅ 可删 | 纯加速用，删了只是变慢 |
| `output/` | ✅ 可删 | 成品，随时可重新生成 |

这个切分的好处：**源数据和产物彻底分离**。清理时只删 `build` / `cache`，绝不碰源；换机器只搬前三层。

## 2. 断点续跑

### 核心：内容寻址，而非位置寻址

缓存键由**内容**决定，与它在台本里的位置无关。

**关键：键必须覆盖「所有影响输出字节的输入」。** 少一项，就会出现「参数变了、键没变」的脏命中。

```python
tts_key = sha1({
    # 文本
    "text":             line_text,
    "preset":           preset,
    # 采样
    "seed":             seed,
    "sampling": {
        "top_k":             15,
        "top_p":             1.0,
        "temperature":       1.0,
        "repetition_penalty":1.35,
        "noise_scale":       0.5,
    },
    # 分段
    "fragment_strategy":   fragment_strategy,
    "max_fragment_characters": max_fragment_characters,
    "rng_strategy":        rng_strategy,
    "whisper_sampling":    whisper_sampling,
    # 运行时
    "engine":              engine_id,      # 部署包版本 / onnxruntime 版本
    "providers":           "hybrid",      # cpu / cuda / hybrid
    "sample_rate":         32000,
})[:20]
```

产物落到 `cache/tts/<key>.wav`。

**同样的输入 → 同样的键 → 直接复用；任何一项变了 → 新键 → 重新合成。**

> ⚠️ **容易漏的项**（都是实测会改变输出字节的）：`noise_scale`、`top_k/p/temperature/repetition_penalty`、`fragment_strategy`、`rng_strategy`、`providers`。只写 text+seed 是不够的。

### ⚠️ 缓存粒度必须对齐「请求粒度」

这是**最容易踩的坑**，源自引擎的采样机制。

引擎（`runtime/engine.py`）对每个 fragment 这样取种子：

```python
for index, target in enumerate(frontend_values):
    SamplingConfig(seed=int(seed) + index, ...)      # 语义 token
    fragment_noise_rng = np.random.default_rng(int(seed) + 100000 + index)  # 解码噪声
```

**`index` 是该 fragment 在本次请求内的序号。** 所以同一句话放在不同位置，产出的字节是不同的。

| 缓存粒度 | 后果 |
|---|---|
| **行级**（一行 = 一次请求 = 一个缓存单元） | ✅ 行内 fragment 序号固定 → 完全可复现 |
| 句级（把行再拆成句单独缓存） | ❌ 句子序号随行内位置漂移 → 与整行合成结果不一致 |
| 多行合并成一次请求 | ❌ 行序号随位置漂移 → 前面插一行，后面全部变 |

**所以：缓存单元必须等于请求单元。**

台本格式定的是「一行 = 一个 TTS 段」，那么**缓存也按整行存**——即使这一行内部被引擎切成了多个 fragment，也作为一个整体缓存。

### 长行会怎样

引擎按标点切分，且 `max_fragment_characters`（默认 240）是二级约束。所以**一行如果含多个句子，请求内会有多个 fragment**——这没问题，只要整行作为一个缓存单元。

但要注意：一行越长，fragment 越多，行内某个句子的「位置」就越依赖前面的内容。**改行内前半句 → 后半句的 fragment 序号不变（序号是按位置给的），但整行的键变了 → 整行重算。** 这是符合预期的。

### 关键设计：一段一请求

这里有个**引擎特性带来的重要约束**，必须说清楚。

Ryza 引擎对每个 fragment 用 `seed + index` 独立采样，其中 `index` 是该 fragment **在单次请求内的序号**。所以：

| 策略 | 后果 |
|---|---|
| 一个请求塞进多个段落 | 段落序号随位置漂移 → 在前面插一句，**后面全部重算** |
| **一段一个请求** | 每个请求只有 1 个 fragment，index 恒为 0 → **完全可复现，插入新段不影响任何旧段** |

台本格式已经定了「一行 = 一个 TTS 段」——**这个选择和缓存策略天然契合**。

### 代价与代价控制

一段一请求会让请求数变多（30 分钟节目可能上百次）。控制手段：

- 引擎常驻时，每次请求的固定开销约 **0.2 秒**（已实测）
- 单段推理本身很快（短文本 1.5 秒量级）
- 综合估算：**30 分钟节目约 5 分钟跑完**

若要更快，可提供「合并模式」：把相邻短段合并到一个请求（累计不超过 510 字）。**代价是缓存粒度变粗**——改一句会导致整块重算。默认关闭。

### 续跑清单 `build/resume.json`

```json
{
  "script_hash": "a1b2c3...",
  "pipeline_version": "1.0",
  "completed": ["key1", "key2", ...],
  "timeline": { "frozen_at": "...", "total_seconds": 1802.4 },
  "updated_at": "2026-10-06T04:50:00Z"
}
```

中断后重跑：逐个查 `cache/tts/`，命中就跳过，未命中才合成。

**每段渲染完立刻落盘**（原子写）——不能等全部跑完才保存，否则中断就白干。

### 静音不进缓存

停顿是**合成的静音**（`np.zeros`），不是真实音频。它由拼接阶段按需生成，不需要占缓存空间。这条能省掉大量无意义文件。

## 3. 混音流程

### 渲染顺序

```
1. 读时间轴 → 算出总时长 T
2. 分配画布：shape = (T × 采样率, 2)，float32 全零
3. 绘 bed 轨 —— 按段落铺环境音，切段处交叉淡化
4. 绘人声轨 —— 按时间轴落点，逐段贴入
5. 绘触发音轨 —— 遍历事件表，按落点贴入
6. 声道处理 —— pan 落位 + pan_swap 换边
7. 总线处理 —— 全局增益 → 削波保护 → 响度归一
8. 写出文件
```

### 为什么是这个顺序

**3/4/5 的先后其实可交换**（加法本身满足交换律），但按这个顺序组织有实际好处：

- 先铺最长、最安静的 bed，后面叠加时更容易判断「谁盖住了谁」
- 人声先于触发音，是因为调试时想先确认「台词都在正确位置」

**6/7 必须在最后**，它们是全局处理，不能逐轨各做一遍再相加：

```
❌ 错：每轨各自归一 → 相加 → 再归一
        （逐轨归一会抹掉轨间音量关系）

✅ 对：每轨应用自己的增益 → 相加 → 总线统一归一
```

### 削波保护的位置

放在**响度归一之后**。因为响度归一可能把峰值推上去（把整体提上来换响度），推完可能越界。

保护手段用**软限幅**（soft limiter），不要硬裁剪——硬裁剪会产生刺耳的高频谐波，在安静的 ASMR 里格外明显。

### 可选：人声触发音闪避（ducking）

人声说话时，把触发音压低几个 dB，说完再恢复。

```
人声起 → 触发音 -4 dB（淡入 80ms）
人声落 → 触发音回归（淡出 250ms）
```

好处是人声更清晰，坏处是触发音的连续性被打断。**默认关闭**，作为可选项——是否启用取决于节目风格（纯耳语类可能不需要，对话类可能需要）。

| 标准 | 目标响度 | 适用 |
|---|---|---|
| ACX | −19 LUFS | 有声书（人声为主） |
| Podcast | −16 LUFS | 播客 |
| ASMR | 通常更轻 | 需自己试 |

ASMR 的响度设计原则与播客相反：追求**亲近感**，所以整体可以做轻，靠动态对比而不是绝对音量。具体数值等你实测听感。

## 5. 开工顺序

原则：**从最小验证开始，每步都产出「能看见的东西」**。别一上来就冲 30 分钟成品。

### 第 0 步：定「要求」怎么写

人类怎么描述一期节目？这是 AI 生成台本的输入，格式得先定。

建议字段：

| 项 | 例 |
|---|---|
| 主题 | 雨夜图书馆 |
| 时长 | 20–30 分钟 |
| 场景 | 安静室内，窗外下雨 |
| 风格 | 低语为主，节奏很慢，多留白 |
| 音效偏好 | 翻书、雨声、轻轻的木质敲击 |
| 其他约束 | 不要出现人声对话；结尾渐弱 |

先起草一份模板，实做时再调。

### 第 1 步：台本生成（AI 写）

把「要求」喂给 AI，产出符合格式的台本。

**验证目标**：AI 能否**稳定**产出格式正确的台本——标点用对、`(sfx)` 位置合理、节奏不失控。

**这一步大概最需要反复迭代**：格式规则要写进 prompt；生成后校验，不合格就让它重写。

### 第 2 步：解析 + 时间轴

台本解析成结构化事件，跑 TTS 拿到每段实测时长。

**验证目标**：解析器认得出所有行类型；时间轴算得对。

### 第 3 步：单行 TTS + 缓存

一行一次请求，产物按内容哈希落盘。

**验证目标**：
- 同输入两次跑，产物字节一致
- 删掉中间产物重跑，能正确跳过已完成的

### 第 4 步：素材匹配 + 剪切预处理

扫描台本里所有 `(sfx ...)`，去素材库找文件。**找到之后必须剪**——这一步不能跳。

**为什么必须剪**：

素材时长参差不齐（几秒到十几分钟），而台本里一个触发音通常只要 1~5 秒。整段贴进去会把大量无用部分也带进来。

**剪切的三个层次**：

```
① 限时长   —— 取 3 秒就是 3 秒                    ✅ 已实现
② 找活动点 —— 自动定位有声区间（仅当素材含长静默时需要） ⚠️ 未实现
③ 无缝循环 —— 环境音要能首尾接上                  ⚠️ 未实现
```

**关于「找活动点」**：不是所有素材都含长静默。实测一个手柄敲击音（babydolldaydreams Steam Deck Fidgeting，49.5s），以噪声底为基准统计，**59% 的帧有声**，384 个连续活动段、间隔中位仅 0.03s——是连续敲击，不存在「孤立点」。

只有当素材确实含大段静默时才需要这个功能。判断方法：看 RMS 分布，若低分位和高分位差距大且中间有明显断层，才值得做活动点检测。

> ⚠️ 踩坑记录：探测活动点**必须用「噪声底」做基准，不能用「峰值」**。曾用 `峰值 × 10^(dB/20)` 定阈值，而被测素材的全局 RMS（0.0038）低于该阈值，导致正常信号全被判成静音，得出「只有 2% 有声」的错误结论。

### 床音（环境音）的特殊处理：`--fit`

环境音（雨声、水族馆、咖啡馆背景）和普通触发音**性质不同**：

| | 普通触发音 | 床音 |
|---|---|---|
| 时长需求 | 1~5 秒 | **贯穿整期**（10~30 分钟） |
| 素材实际长度 | 通常够 | **常常不够** |
| 关键要求 | 不重复听腻 | **无缝、无接缝感** |

**典型的困境**：搜到一个 12 分钟的水族馆音，但要做 10 分钟节目——这里有两种情况：

```
素材比目标长  →  直接截取指定区间（注意起止点的淡入淡出）
素材比目标短  →  循环拼接，接缝处交叉淡化
```

后者是床音特有的。`trim_audio.py` 的 `--fit` 参数把两种情况统一处理：

```bash
# 适配成正好 600 秒：素材长了就截，短了就循环拼接
python data/backups/scripts/trim_audio.py 水族馆.mp3 -o bed.wav --fit 600 --xfade 2.0 --fade 1.0
```

**实测（2026-10-06）**：

| 场景 | 素材 | 目标 | 结果 |
|---|---|---|---|
| A | 12 min | 10 min | ✅ 截取 60~660s，耗时 0.8s |
| B | 8 min | 10 min | ✅ 循环拼接，120s 缺口自动补上，耗时 0.4s |

**实测性能**：12 分钟 48kHz 立体声 wav（132MB）剪切耗时 **0.8 秒**，内存峰值 37MB——长床音完全不是负担。

**接缝交叉淡化为什么必须**：循环点在波形上是个硬接头，不处理会有周期性的咔哒。默认 2 秒交叉淡化，听感上基本察觉不到接缝。

**床音的淡入淡出要比触发音长**：触发音 50ms 够，床音建议 **0.5~2 秒**——环境音突然冒出来或突然消失都很突兀。

**硬性要求：任何剪切都必须带淡入淡出。**

硬切会在切口产生咔哒声（click）——这是波形突然中断的必然结果。**在安静的 ASMR 里，这种咔哒比在普通音乐里刺耳得多**。默认 50ms，环境音可加长。

**第二个要求：同一素材要用不同区间。**

同一个触发音在节目里可能出现十几次。如果每次都用同一段，会听出来「复读」。**不同 offset 取样**能让一个素材听起来不重样——这也是剪切工具要支持 `--start` 的原因。

**验证目标**：
- 剪出来的段落首尾无咔哒（听 + 看波形）
- 同一素材能取出多个不重复区间
- 找得到的绑上、找不到的标出缺口。此时素材库可能还很空——**缺口清单本身就是产出**

### 第 5 步：混音（小规模）

拿 30 秒台本，跑完整链路出成品。

**验证目标**：多轨叠加、声道落位、响度处理都对。

### 第 6 步：上量

组合前面验证过的东西，跑完整 20–30 分钟。

**到这一步才需要考虑**：内存管理、续跑可靠性、整体耗时。

### 为什么是这个顺序

| 步骤 | 为什么放这 |
|---|---|
| 台本生成在最前 | **上游格式错了，下游全白做** |
| 缓存在混音前 | 缓存是加速手段，先验证它对，再上量 |
| 混音单独一步 | 它是「能不能听」的临界点 |
| 上量放最后 | 慢的原因要等有量了才知道 |

## 6. 素材清单与获取策略

### 素材清单字段 `materials/index.yaml`

每个素材记一条，**来源和授权必须留痕**：

```yaml
- id: page_turn_01
  file: sfx/page_turn_01.wav
  desc: 翻书
  tags: [纸质, 翻页, 轻]          # 分类标签，供检索
  source: freesound                # 来源平台
  source_url: https://freesound.org/people/xxx/sounds/12345/
  author: xxx                      # 上传者
  license: CC0                     # CC0 / CC-BY / Pixabay / 自录 / AI生成
  license_url: https://...
  attribution_required: false      # 是否必须署名
  ai_generated: false              # 是否 AI 生成
  commercial_ok: true              # 能否商用
  downloaded_at: 2026-10-06
  # 音频属性（注册时自动测）
  duration_sec: 2.4
  sample_rate: 44100
  channels: 2
  base_lufs: -23.1                 # 基准响度，供音量归一化
```

**几条字段的用意**：

| 字段 | 为什么要有 |
|---|---|
| `license` + `license_url` | 将来要证明来源合法 |
| `ai_generated` | Pixabay 会打 AI 标签，但**不保证准确**；Freesound 也有 AI 素材 |
| `commercial_ok` | 筛掉 NC 类，避免误用 |
| `base_lufs` | 音量归一化的依据（对应台本里的「档位」） |
| `tags` | 素材匹配环节按这个检索 |

### 获取策略：API 检索 + 按需下载

**不该全量下载**（73 万条不可能全下），也**不该每次用都现查**（时间轴冻结要求素材稳定）。平衡点是：

```
写台本 → AI 写描述（如「翻书」）
      ↓
素材匹配 → 查本地清单，命中就用
      ↓ 未命中
      ├─ Freesound → API 检索（可按 license 过滤）
      └─ Pixabay  → 网页手动搜（API 不开放音效）
      → 挑中 → 下载到 materials/ → 写入 index.yaml
      ↓
入库后就固定，后续不再依赖 API
```

**为什么入库后不再依赖 API**：

- 素材可能被作者下架或修改，冻结时间轴会失效
- API 有速率限制，批量作业会被卡住
- 本地素材可反复试听、微调、对比

**两个平台的获取方式不同**：

| 平台 | 检索方式 | 能否脚本化 |
|---|---|---|
| **Freesound** | API `/apiv2/search/` | ✅ 能 |
| **Pixabay** | 网页手动搜 | ❌ 不能（API 不开放音效） |

代价是要**抽查授权**——Pixabay 明确禁止「系统性批量下载」，所以别写个循环把某标签全撸下来。
