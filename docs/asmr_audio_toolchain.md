## 这个文档在讲什么（人话版）

把几十条声音混成一条成品，得有工具。这份文档就回答两个问题：

**用什么混？** → Python 的 numpy。因为「把声音放在第几秒」这件事，用数组操作最直接，而且 AI 写这种代码不容易出错。ffmpeg 只在最后转格式时用一下。

**存成什么规格？**

| 项目 | 选择 | 一句话理由 |
|---|---|---|
| 采样率 | 44.1 kHz | 够覆盖人耳能听的全部频率 |
| 中间格式 | 32 位浮点 | 混音时不会削波、不累积误差 |
| 成品格式 | 16 位 wav | 兼容性最好，音质够用 |

下面开始是完整推导。

## 需求

| 层级 | 要求 |
|---|---|
| 基础 | 多音轨叠加、左右声道独立控制 |
| 进阶 | AI 能用明白（生成的代码不易出错）、占用低、速度快 |
| 规模 | 30 分钟节目，32kHz 立体声 |

**规模换算**：30 分钟 × 60 × 32000 × 2 声道 × 4 字节（float32）≈ **460 MB**。多轨叠加时若每条轨都展开成长数组，峰值可能上 GB。

## 建议：numpy + soundfile 为核心

**理由**：

1. **时间轴控制最直接**——精确落点、稀疏插入，本质上就是数组切片赋值
2. **左右声道 = 数组的第 2 维**，声像调整就是两个通道的增益
3. **素材循环 = `np.tile` 或切片**，不产生额外复杂度
4. **AI 友好**——numpy 语义清晰，出错时容易定位；ffmpeg 的 `filter_complex` 链条长、报错晦涩，让 AI 生成容易翻车
5. **soundfile 读写 float32 wav 无损**，中间产物不必反复编解码

**分工**：

```
numpy/soundfile   →  混音核心（多轨、声道、时间轴）
ffmpeg            →  最终编码（如需 mp3/ogg）
```

ffmpeg 只做最后一步「转格式」，不参与混音逻辑。

## 内存策略

### 1. 稀疏事件模型

不要把每条触发音都展开成「整段长度的数组」。维护一份事件表：

```
(start_sec, duration_sec, material_id, gain_db, pan)
```

渲染时才按需展开到对应区间。30 分钟节目里的触发音大多是短事件，稀疏表示能省掉大量零填充。

### 2. 分块渲染

按分钟（或按固定长度）分块处理，处理完就写入磁盘，不在内存里同时持有整条成品。

### 3. 素材缓存

素材文件只在载入时读一次，循环引用同一个数组。

**结论**：以上三点做完，30 分钟节目在 8GB 内存上跑毫无压力。

## 采样率

### 已知约束

Ryza TTS 的**人声输出固定 32 kHz**（`artifacts/manifest.json` 的 `sampling_rate: 32000`）。这是源头，无法凭空提高。

奈奎斯特定理：采样率 ÷ 2 = 能还原的最高频率。

| 采样率 | 频率上限 | 覆盖情况 |
|---|---|---|
| 32 kHz | 16 kHz | 人声够；高频细节会丢 |
| **44.1 kHz** | **22.05 kHz** | **覆盖人耳听觉上限（约 20 kHz）** |
| 48 kHz | 24 kHz | 超出人耳，纯冗余 |

### 权衡

**人声侧**：32 kHz 已是源头上限。把它升采样到 44.1/48 kHz **不会新增任何信息**，只是插值。所以单看人声，32 kHz 就够。

**触发音侧**：素材多来自 DLsite 同人音声（KU100 人头麦录音）和网络，**常见规格就是 44.1/48 kHz**。这些素材里的高频成分——纸张摩擦的沙沙、玻璃的叮、金属光泽——是**真实携带信息**的，降到 32 kHz 会真的丢掉。

### 推荐：44.1 kHz

1. 覆盖到 22.05 kHz，已在人耳上限之上，**无需 48 kHz 的额外开销**
2. 是绝大多数素材与播放设备的**原生采样率** → 减少重采样次数（重采样正是引入失真的地方）
3. 比 48 kHz 少约 8% 数据量，听感无差别

> ⚠️ **混音前必须把所有素材重采样到同一采样率**。不同采样率直接叠加会逐轨变速、整体错位。

## 位深

位深决定**动态范围**（最轻到最响的可表示跨度）与**量化噪声底**。

| 位深 | 理论动态范围 |
|---|---|
| 16-bit PCM | 96 dB |
| 24-bit PCM | 144 dB |
| 32-bit float | 有效精度约 24-bit，但**无上下限裁剪** |

### 关键区分：中间处理 vs 最终输出

| 阶段 | 推荐 | 理由 |
|---|---|---|
| **中间（混音/处理）** | **32-bit float** | 多轨叠加的中间值可能超出 ±1.0，整数格式会直接削波；反复的增益 / EQ 不累积量化误差 |
| **最终输出** | **16-bit PCM** | ASMR 成品动态范围通常 40–60 dB，96 dB 绰绰有余；兼容性最好 |

**为什么中间必须用 float**：

- 多条轨相加时，瞬时和可能超过 1.0。float 能如实表示，16-bit 会削波——削掉的高峰听不出来但修不回来
- 混音、增益、EQ 每一步都会重新量化一次。16-bit 的舍入误差会**逐步累积**，float 几乎不累积

**为什么最终 16-bit 足够**：

- ASMR 的动态需求远低于古典乐（那才需要 24-bit 的大动态）
- 24-bit 输出在部分播放器 / 平台兼容性不佳

> **例外**：DLsite 素材包常见 24-bit 规格。如果后期处理较重，中间环节至少保 24-bit，**避免「降位后再升位」的二次损失**。

### 小结

```
中间：32-bit float WAV      （混音无忧，无削波，无累积误差）
最终：16-bit PCM WAV        （兼容广，动态足够）
```
